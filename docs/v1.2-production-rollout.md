# LeadBridge v1.2 Production Rollout

This release adds Event scoping and persistent user notifications. The current
schema is single-tenant and has no Organization model. The event backfill
therefore creates one deterministic legacy event and does not invent a tenant.

## Backup And Maintenance

1. Confirm a current Supabase backup or point-in-time recovery window.
2. Record the current production migration status.
3. Confirm `main` contains the reviewed v1.2 merge commit.
4. Pause operator writes during the Event backfill.
5. Never use `prisma db push`, `migrate reset`, or manual data deletion.

## Migration Order

Apply committed migrations in this exact order:

1. `20260721070000_add_event_model_and_backfill`
2. `20260721070100_add_notification_model`

The first migration creates `leadbridge-legacy-event`, assigns existing VR, QR,
and QR registration rows to it, and only then applies `NOT NULL` and foreign
keys. The legacy event is `COMPLETED`, preserving history without accepting new
public or operational writes. The second migration creates Notification with
restrictive User ownership and an optional Event relation.

## Safety Review

- No `DROP TABLE`, `TRUNCATE`, or `DELETE` exists.
- Backfill updates only rows whose `eventId` is null.
- Existing domain rows are not deleted.
- Event foreign keys use `ON DELETE RESTRICT`.
- Notification User ownership uses `ON DELETE RESTRICT`.

## Deployment Sequence

1. Enter the maintenance window.
2. Run `npx prisma migrate status` against the intended production project.
3. Verify these are the only pending migrations.
4. Run `npx prisma migrate deploy` once.
5. Confirm no pending or failed migration remains.
6. Deploy the reviewed v1.2 application build.
7. Create and verify a DRAFT event, then advance it to ACTIVE with a reason.
8. Select the ACTIVE event before resuming operational writes.

This feature branch does not deploy either migration.

## Acceptance Checks

- ADMIN can create, edit, and advance events through the allowlist.
- STAFF cannot manage events and can select only ACTIVE events.
- New VR, QR, and public registrations receive the correct event.
- Public registration rejects non-ACTIVE event QR cards.
- Cross-event QR assignment and student matching are rejected.
- Dashboard, reports, and operational lists use the selected event.
- A user sees and marks only their own notifications.
- Audit writes remain atomic and contain no personal or token data.

## Rollback

Do not drop the additive schema. If acceptance fails, roll back the application
deployment while leaving the schema in place, keep operations paused, and
diagnose the failure. The legacy event keeps existing records addressable.

## Known Risks

- Organization-level isolation is not claimed because no Organization model
  exists in the current product schema.
- Migration duration depends on production row counts.
- Notifications are in-app and best-effort; email and push are not configured.
