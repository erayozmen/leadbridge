# LeadBridge v1.2 Full Database Rollback Plan

This runbook is a plan only. It does not authorize or include a destructive
migration. The current compatibility release keeps Event, Notification, and all
`eventId` values in place.

## Preconditions

1. Schedule a maintenance window and stop all application writes.
2. Verify a current Supabase backup and point-in-time recovery window in the
   platform panel.
3. Export the complete Event and Notification tables and record row counts.
4. Export the `id` and `eventId` mappings for VrRecord, QrCode, and
   QrRegistration.
5. Record `_prisma_migrations`, User, AuditLog, and domain table row counts.
6. Prepare and test the rollback against a restored production snapshot before
   touching production.

## Application Order

Deploy a schema-compatible maintenance build first. It must stop creating or
reading Notification rows and must no longer require Event relations for new
writes. Do not deploy the historical v1.1 commit while `eventId` remains
required, because that code cannot satisfy the current database contract.

## Destructive Migration Order

After the maintenance build is verified on a restored snapshot:

1. Drop only the foreign keys from VrRecord, QrCode, and QrRegistration to
   Event.
2. Drop the related `eventId` indexes.
3. Drop the `eventId` columns only after exported mappings and row counts have
   been verified.
4. Drop Notification foreign keys and indexes.
5. Drop the Notification table.
6. Drop Event indexes and then the Event table.
7. Drop EventStatus only after confirming no remaining column uses it.
8. Preserve User, School, StudentMatch, AuditLog, QR, attendance, and course
   enrollment data throughout the operation.

Each step must be represented by a reviewed Prisma migration. Never use
`db push`, `migrate reset`, `DROP ... CASCADE`, or ad hoc SQL in production.

## Verification And Rollback

Verify migration status, table row counts, QR relationships, public
registration, matching, attendance, course enrollment, reversals, reports, and
ADMIN/STAFF authorization before reopening writes. If any count or relationship
differs, stop the rollout and restore the pre-maintenance backup or PITR point.
Keep the v1.2 application and additive schema in place until the restored
environment passes the complete acceptance suite.

## v1.1 Compatibility

Only after the destructive migration succeeds may a v1.1-compatible build be
deployed. Run production smoke tests for login, dashboard, VR, QR, public
registration, matching, attendance, course enrollment, reports, exports, audit,
and all four reversal operations before ending the maintenance window.
